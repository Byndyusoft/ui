# Configurable Layout Specification

## Purpose

Позволяет проекту-потребителю создавать собственные типизированные компоненты раскладки (View и Flex) из проектной конфигурации сетки отступов — с собственным юнитом и произвольным набором именованных токенов, с автоматической генерацией CSS под эту сетку.

## Requirements

### Requirement: Фабрика компонента раскладки из конфигурации сетки

Библиотека SHALL предоставлять фабрику, принимающую конфигурацию сетки отступов (значение юнита и набор именованных токенов с числовыми множителями юнита) и возвращающую компонент раскладки View, который принимает spacing-пропсы (margin/padding и их варианты по сторонам).

#### Scenario: Создание компонента с проектной сеткой

- **WHEN** потребитель вызывает фабрику с конфигурацией `{ unit: '8px', values: { sm: 0.5, md: 1, lg: 1.5 } }`
- **THEN** возвращается компонент View, принимающий spacing-пропсы со значениями из ключей сетки (`'sm' | 'md' | 'lg'`)

#### Scenario: Имена токенов произвольны

- **WHEN** потребитель задаёт в сетке ключи по своей схеме именования (например, `'025'`, `'gutter'`, `'s16'`)
- **THEN** компонент принимает ровно эти имена как значения spacing-пропсов

### Requirement: Типизация пропсов по конфигурации сетки

Типы spacing-пропсов возвращаемых компонентов SHALL выводиться статически из литерала конфигурации без шага кодогенерации: допустимы только ключи заданной сетки, значения вне сетки MUST отклоняться компилятором.

#### Scenario: Автокомплит и ошибки компиляции

- **WHEN** потребитель передаёт spacing-пропсу значение, отсутствующее среди ключей сетки
- **THEN** TypeScript сообщает об ошибке типа на этапе компиляции

### Requirement: Фабрика Flex от экземпляра View

Библиотека SHALL предоставлять фабрику `createFlex`, принимающую экземпляр View, созданный `createView`, и возвращающую компонент Flex с gap-пропсами (`gap`, `rowGap`, `columnGap`), типизированными той же сеткой. Отдельная передача конфигурации в `createFlex` MUST NOT требоваться.

#### Scenario: Единый источник сетки для View и Flex

- **WHEN** потребитель вызывает `createFlex(view)`, где `view` — результат `createView(config)`
- **THEN** gap-пропсы Flex принимают те же токены, что spacing-пропсы View, а изменение конфигурации в одном месте меняет типы обоих компонентов

#### Scenario: Flex-пропсы раскладки сохранены

- **WHEN** потребитель использует созданный Flex с пропсами `direction`, `wrap`, `alignContent`, `alignItems`, `justifyContent`
- **THEN** компонент применяет соответствующие CSS-классы раскладки

### Requirement: Ref на DOM-элемент фабричного компонента

Компоненты View и Flex, созданные фабриками, SHALL принимать object и callback refs типа `HTMLElement` и передавать их на фактически отрендеренный HTML-элемент. Для Flex ref MUST указывать на элемент, который рендерит созданный View; ref MUST NOT предоставлять внутренний API компонента или фабрики.

#### Scenario: Object ref с пользовательским тегом View

- **WHEN** потребитель передаёт созданному View object ref и `as="section"`
- **THEN** ref указывает на отрендеренный элемент `section` типа `HTMLElement`

#### Scenario: Ref компонента Flex

- **WHEN** потребитель передаёт созданному Flex object ref и задаёт нативный тег через `as`
- **THEN** ref указывает на этот HTML-элемент, созданный View, без дополнительной DOM-обёртки

#### Scenario: Callback ref при монтировании и размонтировании

- **WHEN** потребитель передаёт созданному View или Flex callback ref
- **THEN** callback получает фактический HTML-элемент при монтировании и `null` при размонтировании

#### Scenario: Типизация ref

- **WHEN** TypeScript проверяет вызов созданного View или Flex с ref
- **THEN** ref принимается как ссылка на `HTMLElement` независимо от выбранного `as`, без публичной типизации внутреннего компонента

### Requirement: Генерация CSS из конфигурации

Библиотека SHALL генерировать из конфигурации плоский CSS без препроцессоров: классы отступов для каждого токена и варианта стороны, классы gap для Flex, фиксированные классы flex-модификаторов. Значения MUST вычисляться как `calc(var(--bsui-unit, <unit>) * <multiplier>)`.

#### Scenario: Класс соответствует токену и множителю

- **WHEN** конфигурация содержит токен `lg` с множителем `1.5` и юнитом `8px`
- **THEN** сгенерированный CSS содержит класс, задающий соответствующее свойство значением `calc(var(--bsui-unit, 8px) * 1.5)`

#### Scenario: Разметка без inline-стилей

- **WHEN** компонент рендерится со spacing-пропсами
- **THEN** элемент получает только сгенерированные CSS-классы, атрибут `style` не используется

### Requirement: Автоинъекция CSS при импорте модуля

Сгенерированный CSS SHALL автоматически добавляться в документ при импорте модуля с созданными компонентами в браузерном окружении. Импорт в окружении без DOM (node) MUST NOT приводить к ошибке или обращению к DOM.

#### Scenario: Автоинъекция в браузере

- **WHEN** потребитель импортирует модуль с созданными компонентами в браузерном окружении
- **THEN** сгенерированный CSS добавлен в документ и классы применяются

#### Scenario: Безопасность в окружении без DOM

- **WHEN** модуль импортируется в node-окружении (серверный рендер, тесты)
- **THEN** ошибки не возникает и обращения к DOM не происходит

### Requirement: Рендер стилей для SSR

Библиотека SHALL предоставлять React-компонент стилей, рендерящий сгенерированный CSS в элемент `<style>` внутри дерева приложения, чтобы серверный рендер включал стили в HTML. После гидратации стили MUST NOT дублироваться.

#### Scenario: Стили в серверном HTML

- **WHEN** SSR-приложение включает компонент стилей в корень и рендерится на сервере
- **THEN** итоговый HTML содержит элемент `<style>` со сгенерированным CSS

#### Scenario: Без дублей после гидратации

- **WHEN** страница, отрендеренная на сервере с компонентом стилей, гидратируется на клиенте
- **THEN** автоинъектор распознаёт существующие стили и не добавляет их повторно

### Requirement: Рантайм-переопределение юнита

Значение юнита SHALL оставаться переопределяемым в рантайме через CSS-переменную: переопределение переменной меняет все отступы без пересоздания компонентов и перегенерации CSS.

#### Scenario: Переопределение юнита для поддерева

- **WHEN** потребитель задаёт CSS-переменную юнита на контейнере
- **THEN** все отступы компонентов внутри контейнера пересчитываются от нового значения

### Requirement: Валидация ключей сетки

Фабрика MUST отклонять ключи сетки, которые не могут быть использованы в именах CSS-классов без экранирования (пробелы, точки, двоеточия и подобные), с понятной ошибкой в момент создания компонента.

#### Scenario: Недопустимый ключ отклоняется

- **WHEN** конфигурация содержит ключ с недопустимыми символами (например, `'my token'`)
- **THEN** фабрика бросает ошибку с указанием недопустимого ключа

### Requirement: Короткие aliases spacing-пропсов

Созданные компоненты `View` и `Flex` SHALL принимать короткие aliases для margin и padding; каждый alias SHALL иметь тот же смысл и тип токена, что соответствующий полный prop.

#### Scenario: Короткие aliases внешних отступов

- **WHEN** потребитель передаёт `m`, `mt`, `mr`, `mb`, `ml`, `mh` или `mv` со значением из `values`
- **THEN** компонент применяет отступ, эквивалентный соответствующему prop `margin`, `marginTop`, `marginRight`, `marginBottom`, `marginLeft`, `marginHorizontal` или `marginVertical`

#### Scenario: Короткие aliases внутренних отступов

- **WHEN** потребитель передаёт `p`, `pt`, `pr`, `pb`, `pl`, `ph` или `pv` со значением из `values`
- **THEN** компонент применяет отступ, эквивалентный соответствующему prop `padding`, `paddingTop`, `paddingRight`, `paddingBottom`, `paddingLeft`, `paddingHorizontal` или `paddingVertical`

#### Scenario: Типизация aliases

- **WHEN** потребитель задаёт короткий alias значением, отсутствующим в `values`
- **THEN** TypeScript сообщает об ошибке типа

#### Scenario: Короткие props не передаются в DOM

- **WHEN** компонент рендерится с короткими spacing aliases
- **THEN** aliases используются для вычисления классов и не попадают в DOM-атрибуты

### Requirement: Разрешение двух aliases одного spacing-свойства

Если полный prop и его короткий alias заданы одновременно, компонент SHALL использовать значение последнего определённого prop в порядке перечисления собственных ключей итогового объекта props; `undefined` SHALL считаться отсутствующим значением. Компонент MUST NOT выбрасывать ошибку только из-за присутствия обеих форм.

#### Scenario: Alias указан после полного prop

- **WHEN** итоговый объект props содержит `margin: 'sm'`, а затем `m: 'md'`
- **THEN** эффективным значением свойства margin становится `'md'`

#### Scenario: Полный prop указан после alias

- **WHEN** итоговый объект props содержит `m: 'md'`, а затем `margin: 'sm'`
- **THEN** эффективным значением свойства margin становится `'sm'`

#### Scenario: Поздний alias равен undefined

- **WHEN** итоговый объект props содержит определённый `margin` и более поздний `m: undefined`
- **THEN** значение `margin` остаётся эффективным

### Requirement: Приоритет общих и направленных spacing-пропсов

После разрешения пар aliases компонент SHALL определять эффективный токен каждой стороны: общий prop margin или padding имеет приоритет над всеми его вариантами; horizontal и vertical props имеют приоритет над соответствующими физическими сторонами. Эти правила MUST применяться одинаково к margin и padding независимо от порядка их props.

#### Scenario: Общий margin имеет приоритет над направленными props

- **WHEN** заданы `margin`, `marginTop` и `marginHorizontal` с разными токенами
- **THEN** токен `margin` применяется ко всем четырём сторонам

#### Scenario: Horizontal margin имеет приоритет над left и right

- **WHEN** заданы `marginHorizontal`, `marginLeft` и `marginRight` с разными токенами, но `margin` не задан
- **THEN** токен `marginHorizontal` применяется к левой и правой сторонам

#### Scenario: Vertical padding имеет приоритет над top и bottom

- **WHEN** заданы `paddingVertical`, `paddingTop` и `paddingBottom` с разными токенами, но `padding` не задан
- **THEN** токен `paddingVertical` применяется к верхней и нижней сторонам

### Requirement: Компактное представление эффективных spacing-токенов

Компонент SHALL формировать непересекающийся минимальный набор spacing-классов из эффективных токенов сторон. Стороны считаются одинаковыми только при совпадении имён токенов, а не только их числовых множителей.

#### Scenario: Все четыре стороны имеют одинаковый токен

- **WHEN** эффективные токены всех четырёх сторон margin совпадают
- **THEN** компонент добавляет один общий класс `bsui-m-<token>` вместо классов отдельных сторон

#### Scenario: Горизонтальная пара сворачивается в shorthand-класс

- **WHEN** эффективные токены левой и правой сторон совпадают, а один общий токен не покрывает все четыре стороны
- **THEN** компонент использует класс `mh` или `ph` для горизонтальной пары и отдельные классы только для оставшихся заданных сторон

#### Scenario: Вертикальная пара сворачивается в shorthand-класс

- **WHEN** эффективные токены верхней и нижней сторон совпадают, а один общий токен не покрывает все четыре стороны
- **THEN** компонент использует класс `mv` или `pv` для вертикальной пары и отдельные классы только для оставшихся заданных сторон

#### Scenario: Все четыре стороны padding имеют одинаковый токен

- **WHEN** эффективные токены всех четырёх сторон padding совпадают
- **THEN** компонент добавляет один общий класс `bsui-p-<token>` вместо классов отдельных сторон

#### Scenario: Оставшиеся разные стороны

- **WHEN** эффективные токены не образуют общего или парного shorthand-класса
- **THEN** компонент добавляет классы для соответствующих физических сторон без изменения их вычисленных значений

#### Scenario: Совпадающие множители с разными токенами не схлопываются

- **WHEN** эффективные токены сторон имеют разные имена, даже если их множители в `values` совпадают
- **THEN** компонент не заменяет их общим или парным классом только на основании совпадения множителей
