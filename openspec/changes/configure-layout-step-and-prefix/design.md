# Design

## Context

См. `proposal.md` — Why. Сейчас `IViewConfig` содержит строковый `unit` и `values`; генераторы View и Flex вызывают общий `getSpacingValue`, который возвращает `calc(var(--bsui-unit, ...))`. Имена View-классов формируются с захардкоженным `bsui`, а базовый класс и модификаторы Flex — статическими строками. `createFlex` уже получает конфигурацию через созданный View. Публичные утилиты `getSpacingValue`, `getSpacingClassName`, `blockClassName` и `flexModifiersCss` экспортированы из пакетов.

## Goals / Non-Goals

**Goals:**

-   Сохранить один источник конфигурации для View и Flex и использовать его для готовых CSS-длин и namespace классов.
-   Сохранить совместимость классов при опущенном `prefix` и прежние default-вызовы публичных утилит.
-   Убрать `calc()` и зависимость от `--bsui-unit` из CSS, создаваемого фабриками.

**Non-Goals:**

-   Добавлять CSS-единицы помимо `px` и `rem`.
-   Менять набор spacing-токенов, их типизацию, aliases или правила выбора компактных классов.
-   Менять SSR, автоинъекцию или формат идентификаторов `<style>`.

## Decisions

### Шаг хранится числом и единицей

`IViewConfig` заменяет строковое поле `unit` на `step: { value: number; unit: 'px' | 'rem' }`; `prefix` остаётся необязательным со значением по умолчанию `bsui`. Ограничение положительного целого `step.value` проверяется фабрикой во время выполнения; union типа ограничивает единицу CSS на этапе TypeScript и runtime-валидацией для нетипизированных потребителей.

Альтернатива — оставить строку вроде `8px` и разбирать её при построении стилей. Объект шага делает числовое значение и поддерживаемую единицу явными и исключает разбор произвольного CSS.

### CSS-длины вычисляются в генераторе

Существующая экспортированная утилита `getSpacingValue` получает overload для объекта `step`: он умножает целое `step.value` на множитель `values`, нормализует числовую строку, чтобы не выдавать артефакты двоичной арифметики, и добавляет `step.unit`. CSS-генераторы View и Flex используют этот overload и готовую длину напрямую; существующий overload со строковым юнитом сохраняет прежнее поведение. Дробные множители остаются допустимыми.

Альтернатива — хранить вычисление в CSS через `calc()` или переменную. Она сохраняет runtime-переопределение, которое не входит в новый контракт, и оставляет повторяющиеся выражения в сгенерированном CSS.

Экспортированный `getSpacingValue(unit, multiplier)` сохраняет standalone-поведение для существующих потребителей; фабрики используют overload `getSpacingValue(step, multiplier)`. Константа `spacingUnitVariable` сохраняется как экспорт, но не управляет сгенерированными классами.

### Namespace задаётся конфигурацией View и наследуется Flex

`prefix` является частью конфигурации View, поэтому `createFlex(view)` получает тот же namespace без нового аргумента. Пространственные имена формируются как `<prefix>-<spacing-variant>-<token>` для View и `<prefix>-flex...` для Flex. Без `prefix` результат остаётся `bsui-*`. Значение валидируется до регистрации стилей; для простого CSS-селектора допускаются латинская буква или `_` в начале и латинские буквы, цифры, `_`, `-` далее.

Чтобы не ломать default-поведение экспортированных утилит, `getSpacingClassName` и функции получения Flex-модификаторов получают необязательный параметр namespace с default `bsui`. Экспортированные `blockClassName` и `flexModifiersCss` продолжают представлять прежний default namespace; фабрика собирает CSS модификаторов с namespace из конфигурации.

Альтернатива — сделать namespace обязательным или принимать его повторно в `createFlex`. Обязательное поле изменит все конфигурации, а отдельное значение для Flex создаст риск расхождения с View.

### Идентичность зарегистрированных стилей включает конфигурацию

Текущий реестр ключует записи сериализованной конфигурацией. Новые `step` и `prefix` остаются частью этого ключа, поэтому отличающиеся настройки получают отдельные style entries и стабильные ID; совместная регистрация CSS View и Flex для одной конфигурации продолжает использовать существующий механизм.

## Risks / Trade-offs

-   [Переход с `unit` на `step` и отказ от `--bsui-unit` меняют публичный контракт] → Обновить примеры и README View/Flex, явно описать миграцию и добавить changeset обоих пакетов.
-   [Несовпадающие или некорректные namespaces могут приводить к конфликтующим либо невалидным селекторам] → Валидировать `prefix`; при нескольких сетках потребитель задаёт уникальные значения.
-   [Числовая погрешность при умножении дробных токенов может попасть в CSS] → Нормализовать результат форматтером и закрепить дробные случаи тестами.
-   [Экспортированные статические Flex-утилиты не могут сами знать runtime-prefix] → Сохранить их прежний default-контракт и добавить optional namespace аргументы к функциям, используемым фабриками.

## Migration Plan

1. Перевести конфигурации с `unit: '8px'` на `step: { value: 8, unit: 'px' }`; для `rem` задать, например, `{ value: 1, unit: 'rem' }`.
2. При одновременном использовании нескольких сеток на странице задавать каждой уникальный `prefix`; иначе default `bsui` сохраняет существующие имена классов.
3. Удалить стили, полагавшиеся на runtime-переопределение `--bsui-unit`; создавать фабрики с нужным шагом.
4. Выпустить изменения `@byndyusoft-ui/view` и `@byndyusoft-ui/flex` как breaking release. Откат — вернуть прежнюю версию пакетов и конфигурацию со строковым `unit`.
