# Spec Delta

## Purpose

Компонент TextEditor позволяет вводить форматированный текст визуально и сохранять его как Markdown в формах сайтов. Поле ограничивает доступные инструменты, сохраняет существующее оформление и поддерживает отложенные уведомления и автоматическую высоту.

## ADDED Requirements

### Requirement: Публичный пакет и совместимость

Пакет `@byndyusoft-ui/text-editor` MUST предоставлять default и именованный экспорт `TextEditor`, типы `ITextEditorProps`, `TTextEditorTool` и ref на редактируемый `HTMLDivElement`. Публичный API MUST работать с React 17 и TypeScript 4.9 без обязательного обновления потребителя.

#### Scenario: Использование публичной точки входа

-   **WHEN** потребитель импортирует компонент и типы из `@byndyusoft-ui/text-editor` в приложении React 17
-   **THEN** именованный и default экспорты предоставляют один компонент, декларации типов разрешаются, а object-ref и callback-ref получают область ввода и очищаются при размонтировании

### Requirement: Визуальное редактирование Markdown

TextEditor MUST визуально редактировать жирный, курсивный, подчёркнутый и зачёркнутый текст, абзацы, нумерованные и ненумерованные списки, ссылки и заголовки H1–H6. Внешнее значение MUST быть строкой Markdown; подчёркивание MUST записываться как `++текст++`, зачёркивание — как `~~текст~~`, пустой документ — как `''`.

#### Scenario: Сохранение и повторная загрузка поддерживаемых форматов

-   **WHEN** пользователь создаёт документ со всеми поддерживаемыми форматами, вложенными списками и сочетаниями inline-форматирования, затем сохраняет и повторно открывает Markdown
-   **THEN** текст, ссылки, порядок, уровни заголовков, структура списков и форматирование сохраняются; запись Markdown может нормализоваться без потери смысла

#### Scenario: Абзац и перенос строки

-   **WHEN** пользователь нажимает Enter в обычном абзаце или Shift+Enter внутри него
-   **THEN** Enter создаёт новый абзац, Shift+Enter создаёт перенос внутри абзаца, а оба результата сохраняются после повторного открытия

#### Scenario: Пустой документ

-   **WHEN** пользователь удаляет текст и оставляет документ с одним пустым обычным абзацем
-   **THEN** уведомление передаёт `''`, область остаётся доступной для ввода и показывает placeholder при его наличии

### Requirement: Конфигурация инструментов поля

Prop `tools` MUST принимать массив значений `bold`, `italic`, `underline`, `strike`, `heading`, `orderedList`, `bulletList`, `link`. Без prop MUST быть доступны только первые четыре инструмента в указанном порядке. Абзацы MUST оставаться доступными всегда. Явный пустой массив MUST отключать все инструменты форматирования.

#### Scenario: Набор по умолчанию

-   **WHEN** поле отображается без `tools`
-   **THEN** панель предоставляет только жирный, курсив, подчёркивание и зачёркивание; пользователь может вводить обычный текст и абзацы

#### Scenario: Явная конфигурация

-   **WHEN** поле получает `tools={['link', 'bold']}`, а затем `tools={[]}`
-   **THEN** сначала доступны ссылка и жирный в указанном порядке, затем панель форматирования отсутствует; повторяющиеся инструменты не дублируют элементы панели

### Requirement: Существующее оформление независимо от инструментов

TextEditor MUST загружать, отображать и сохранять все поддерживаемые форматы из `value` или `defaultValue` независимо от `tools`. Изменение `tools` MUST менять доступные действия без очистки документа, перемещения курсора или уведомления об изменении содержимого.

#### Scenario: Редактирование ранее сохранённого заголовка

-   **WHEN** поле без `heading` загружает Markdown с заголовком и пользователь изменяет текст этого заголовка
-   **THEN** существующий заголовок корректно отображается и сохраняет свой уровень в результирующем Markdown

#### Scenario: Отключение инструмента после редактирования

-   **WHEN** родитель удаляет `bold` из `tools` у документа с жирным текстом
-   **THEN** жирный текст и выделение сохраняются, инструмент больше недоступен, а callbacks изменения не вызываются

### Requirement: Ограничения создания нового оформления

TextEditor MUST запрещать применение отсутствующих в `tools` форматов через панель, горячие клавиши, автоматическое распознавание ввода и другие действия интерфейса. Эти ограничения MUST действовать независимо от поддержки формата в существующем документе. Изменение текста уже оформленного фрагмента MUST оставаться возможным.

#### Scenario: Недоступный формат через клавиатуру и ввод

-   **WHEN** `heading`, `link` и `bold` отсутствуют в `tools`, а пользователь пытается создать их горячей клавишей, Markdown-последовательностью или действием интерфейса
-   **THEN** новое оформление не применяется, введённый текст сохраняется, а существующие заголовки, ссылки и жирные фрагменты не удаляются

#### Scenario: Выход из недоступного существующего блока

-   **WHEN** `heading` отсутствует в `tools` и пользователь создаёт новый блок после существующего заголовка
-   **THEN** новый блок является обычным абзацем, а исходный заголовок сохраняется

### Requirement: Очистка форматирования при вставке

Вставка из буфера MUST снимать форматы, отсутствующие в актуальном `tools`, сохраняя текст, порядок и доступное оформление. Это MUST применяться к HTML, Markdown и внутреннему копированию между редакторами. Результат вставки MUST не наследовать запрещённые inline-форматы из места вставки.

#### Scenario: Вставка смешанного оформления

-   **WHEN** в поле с `tools={['bold']}` вставляется текст с жирным, курсивом, подчёркиванием, зачёркиванием, ссылкой и заголовком
-   **THEN** сохраняется только жирное оформление, заголовок становится абзацем, ссылка сохраняет видимый текст, а остальное содержимое сохраняется без запрещённых форматов

#### Scenario: Вставка запрещённого списка

-   **WHEN** инструмент соответствующего списка недоступен и пользователь вставляет список, включая вложенные элементы
-   **THEN** текст каждого элемента остаётся отдельным абзацем в исходном порядке, доступное inline-оформление сохраняется

#### Scenario: Внутренняя вставка и оформленная позиция

-   **WHEN** пользователь копирует запрещённое оформление из существующего документа и вставляет его, в том числе внутрь уже оформленного фрагмента
-   **THEN** вставленный фрагмент очищается по `tools`, а оформление содержимого вне вставленного диапазона сохраняется

#### Scenario: Простая вставка и повторное изменение конфигурации

-   **WHEN** пользователь вставляет текст или Markdown после изменения `tools`
-   **THEN** многострочный текст сохраняется, поддерживаемая Markdown-разметка распознаётся, символы без роли разметки остаются текстом, а фильтрация использует новый набор инструментов

### Requirement: Управляемое и неуправляемое значение

TextEditor MUST поддерживать `value` как управляемое значение и `defaultValue` как начальное неуправляемое значение. Внешняя замена `value` MUST обновлять документ без callbacks изменения и отменять ожидающие уведомления о заменённом документе. Возврат родителем текущего пользовательского значения MUST не сбрасывать курсор и таймеры.

#### Scenario: Управляемый ввод

-   **WHEN** родитель немедленно сохраняет Markdown из `onChange` обратно в `value`
-   **THEN** текст и оформление обновляются сразу, курсор и выделение сохраняются, уведомления не зацикливаются и отложенные вызовы остаются запланированными

#### Scenario: Неуправляемый ввод и внешняя замена

-   **WHEN** пользователь редактирует поле с `defaultValue`, либо родитель заменяет `value` другим документом
-   **THEN** в первом случае содержимое хранится внутри поля, изменение `defaultValue` после монтирования его не заменяет; во втором случае новый документ отображается без callbacks и старых отложенных уведомлений

### Requirement: Немедленные уведомления о документе

`onChange` MUST принимать строковый снимок Markdown сразу после пользовательского изменения документа. Ввод, форматирование, вставка, удаление, undo и redo MUST уведомлять при изменении документа. Изменение выделения, фокуса, props или конфигурации MUST не запускать callbacks изменения.

#### Scenario: Изменение документа и выделения

-   **WHEN** пользователь форматирует текст и затем перемещает курсор
-   **THEN** callbacks регистрируются для изменения форматирования, но не для перемещения курсора; аргумент является строкой Markdown, а не DOM-событием

### Requirement: Debounce после паузы

`onDebouncedChange` MUST получать последний пользовательский снимок после полной паузы `debounceDelay` в миллисекундах, по умолчанию 2000. Каждое изменение MUST перезапускать ожидание. При размонтировании ожидающий debounce MUST завершаться ровно один раз; при отсутствии ожидания вызова MUST не быть.

#### Scenario: Новое изменение до истечения паузы

-   **WHEN** пользователь изменяет документ дважды до истечения `debounceDelay`
-   **THEN** callback вызывается один раз с последним снимком после полной паузы от второго изменения, а ввод и высота обновляются сразу

#### Scenario: Размонтирование после ввода

-   **WHEN** поле размонтируется с ожидающим debounce, в том числе синхронно внутри `onChange`
-   **THEN** актуальный обработчик получает последний снимок один раз и таймер не остаётся активным

### Requirement: Throttle с отложенным первым вызовом

`onThrottledChange` MUST получать последний пользовательский снимок в конце окна `throttleDelay` в миллисекундах, по умолчанию 1000. Первый ввод MUST не вызывать callback немедленно; новый ввод внутри окна MUST не сдвигать его срок. При размонтировании ожидающий throttle MUST отменяться.

#### Scenario: Непрерывный ввод

-   **WHEN** несколько изменений происходят внутри одного окна throttle и ввод продолжается после его завершения
-   **THEN** в конце окна передаётся последний снимок, следующее окно начинается с первого следующего изменения и частота вызовов не превышает одного за интервал

#### Scenario: Отмена при размонтировании

-   **WHEN** поле размонтируется до конца окна, в том числе внутри `onChange`
-   **THEN** ожидающий throttle не выполняется и его таймер удаляется

### Requirement: Общие правила отложенных callbacks

Debounce и throttle MUST работать независимо, использовать актуальный callback и не создавать ожидание без соответствующего обработчика. Удаление обработчика MUST отменять ожидание; его замена MUST сохранять срок. Изменение delay MUST влиять на следующие окна. Ноль MUST означать асинхронный вызов; некорректные значения MUST заменяться defaults.

#### Scenario: Независимость и изменение обработчиков

-   **WHEN** работают оба обработчика, один заменяется, а другой удаляется и затем включается снова
-   **THEN** первый использует новую функцию без переноса срока; второй не получает снимок, ожидавший до отключения; независимый ввод и другой таймер продолжают работать

#### Scenario: Интервалы и строковые снимки

-   **WHEN** во время ожидания меняется delay или получает значение `0`, отрицательное число, `NaN` либо бесконечность
-   **THEN** текущий срок сохраняется, следующее ожидание использует нормализованный интервал, ноль остаётся асинхронным и callback получает сохранённую строку, а не данные, считанные из DOM позднее

### Requirement: Автоматическая высота

При `withAutoHeight` TextEditor MUST расти и уменьшаться по содержимому, учитывать CSS min/max-height, padding, border и box-sizing и включать вертикальную прокрутку при переполнении. Пересчёт MUST реагировать на редактирование, оформление, внешнее значение, ширину и стили, независимо от callback-задержек.

#### Scenario: Рост, уменьшение и ограничения

-   **WHEN** пользователь добавляет заголовки и списки, достигает `maxHeight`, затем удаляет содержимое
-   **THEN** область ввода растёт до ограничения, прокручивается при переполнении, затем уменьшается не ниже `minHeight`; панель не попадает в прокручиваемое содержимое

#### Scenario: Изменение ширины и скрытое поле

-   **WHEN** ширина или стили меняются, поле снова показывается после скрытия либо API наблюдения размеров отсутствует
-   **THEN** высота обновляется при очередном доступном измерении без потери фокуса и выделения; отсутствие API не вызывает ошибки

#### Scenario: Выключение авто-высоты

-   **WHEN** `withAutoHeight` выключается или поле размонтируется
-   **THEN** измерения и подписки прекращаются, ожидающий кадр отменяется, а при выключении возвращаются актуальные пользовательские размеры и overflow

### Requirement: Состояния доступности поля

`isDisabled` MUST запрещать пользовательский ввод, форматирование и вставку и исключать поле из последовательной клавиатурной навигации. `isReadOnly` MUST запрещать изменения, сохраняя фокус, выделение и копирование. Оба состояния MUST позволять обновлять содержимое через `value`; disabled MUST иметь приоритет.

#### Scenario: Disabled и read-only

-   **WHEN** поле находится в любом из состояний и пользователь пытается изменить его с панели, клавиатуры или буфера
-   **THEN** документ и callbacks не изменяются; в read-only можно выделить и скопировать текст, в disabled область и инструменты не получают Tab-фокус

### Requirement: Клавиатура и управление фокусом

TextEditor MUST предоставлять доступное имя, многострочную семантику области ввода, обозначения активных инструментов и клавиатурное управление панелью. Панель MUST сохранять выделение для применения команды и не отправлять форму. Undo/redo MUST восстанавливать документ, включая существующие отключённые форматы.

#### Scenario: Форматирование с панели и ссылка

-   **WHEN** пользователь выделяет текст, переходит на инструмент клавиатурой и применяет формат либо создаёт, изменяет или удаляет ссылку
-   **THEN** действие относится к сохранённому выделению, фокус возвращается в редактор, активное состояние доступно вспомогательным технологиям и форма не отправляется

#### Scenario: Undo и ввод составных символов

-   **WHEN** пользователь отменяет или повторяет изменение либо вводит текст через IME
-   **THEN** история восстанавливает содержимое без очистки существующего оформления, а ввод не теряет символы и не прерывает композицию пересозданием области ввода

### Requirement: Нативная интеграция с формой

При `name` TextEditor MUST включать актуальный Markdown в FormData связанной формы без ожидания debounce/throttle. `form` MUST позволять указать форму по id. Disabled-поле MUST не участвовать в отправке. Сброс MUST восстанавливать `defaultValue` в неуправляемом режиме, сохранять `value` в управляемом и отменять ожидания без callbacks изменения.

#### Scenario: Отправка до отложенного уведомления

-   **WHEN** пользователь изменяет поле с `name` и отправляет связанную форму до срабатывания таймеров
-   **THEN** FormData содержит текущий Markdown; disabled-поле отсутствует, а read-only поле включается

#### Scenario: Сброс формы

-   **WHEN** связанная форма сбрасывается или привязка `form` изменяется
-   **THEN** сброс соответствует режиму значения, высота пересчитывается и старые ожидания отменяются; после смены привязки поле реагирует только на новую форму

### Requirement: Безопасная обработка содержимого

TextEditor MUST обрабатывать входное значение и буфер в пределах поддерживаемых форматов без выполнения HTML или скриптов. Ссылки MUST разрешать только `http:`, `https:`, `mailto:`, `tel:`, относительные пути и фрагменты. Неподдерживаемое оформление MUST не становиться активным содержимым; текст внутри него MUST сохраняться, когда он присутствует.

#### Scenario: Недопустимая ссылка и активный HTML

-   **WHEN** входное значение, форма ссылки или буфер содержат `javascript:`/`data:` URL, обработчик HTML-события или активный HTML-элемент
-   **THEN** они не выполняются и не создают активную ссылку; видимый текст сохраняется, недопустимый URL в форме ссылки не применяется

### Requirement: Серверный рендеринг и освобождение ресурсов

Импорт пакета и серверный рендеринг TextEditor MUST не требовать браузерных API. Монтирование на клиенте MUST корректно отображать начальное значение. Размонтирование MUST освобождать экземпляр редактора, таймеры, подписки и наблюдение размеров с сохранением оговорённой семантики debounce.

#### Scenario: Рендеринг без DOM

-   **WHEN** компонент импортируется и рендерится в окружении без window, document и observer API, затем монтируется на клиенте
-   **THEN** серверный рендеринг не падает и начальный документ появляется после клиентской инициализации без callbacks изменения

#### Scenario: Повторное монтирование

-   **WHEN** редактор неоднократно монтируется и размонтируется
-   **THEN** подписки не дублируются, старые экземпляры не изменяют новый документ, throttle не вызывается после очистки, а debounce выполняется только по своему контракту
