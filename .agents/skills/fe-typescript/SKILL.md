# Типизация пакетов

Пути к исходникам ниже указаны относительно этого скилла. Общие команды и устройство
монорепозитория описаны в корневом [AGENTS.md](../../../AGENTS.md).

## Конфигурация и выпуск деклараций

-   Пакетный `tsconfig.json` наследует корневой конфиг с `strict: true`, TypeScript 4.9 и `jsx: react`.
    Для JSX сохраняй совместимость с React 17 и установленными `@types/react`.
-   Публикуемые TypeScript-пакеты генерируют декларации в `dist`; поле `types` в манифесте
    должно указывать на существующую точку входа, обычно `dist/index.d.ts`.
-   У хуков обычно есть отдельный `tsconfig.build.json`, у компонентов декларации выпускает
    `@rollup/plugin-typescript`. Проверяй исключения для историй, MDX, runtime-тестов,
    `*.tests-d.ts` и тестовых помощников: конфигурации пакетов отличаются.
-   Не меняй `module`, `type`, `main`, `module` и `exports` в манифесте независимо друг от друга.
    В репозитории одновременно есть ESM и CommonJS; сохраняй формат существующего пакета.
-   Импортируй чужие workspace-пакеты по `@byndyusoft-ui/...`; публичные типы должны быть
    доступны через их точку входа. Зависимость, используемая в `.d.ts`, должна разрешаться
    у потребителя пакета и быть объявлена в его манифесте.

## Форма типов

-   Для объектных контрактов предпочитай `interface`, для union, tuple, функций,
    mapped и conditional types — `type`. Учитывай правила [fe-naming](../fe-naming/SKILL.md)
    для `I` и `T`; исторические общие типы вроде `Callback` сохраняй совместимыми.
-   Публичные props и связанные контракты обычно размещай в `src/<Сущность>.types.ts`.
    Небольшие внутренние типы могут оставаться рядом с реализацией.
-   На публичных функциях указывай возвращаемый тип. Локальный вывод типов оставляй там,
    где он прозрачен; не дублируй каждую выведенную аннотацию.
-   Не используй `any` для обхода контракта. Для неизвестных данных используй `unknown`
    и сужение; приведения и non-null assertions не заменяют проверку возможного `null`.
-   Различай необязательный параметр, `undefined` и `null` по поведению API.
    DOM-ref до появления элемента может содержать `null`.
-   Перед добавлением общего типа проверь [packages/types/src/index.ts](../../../packages/types/src/index.ts):
    там уже есть `Callback`, `Nullable`, `Predicate`, `Comparator`, `InitialState` и другие утилиты.

## Props и generic API

-   Для нативного элемента расширяй соответствующие React HTML attributes.
    Если библиотечный prop заменяет нативный, исключай нативный через `Omit`, как в
    [TextInput.types.ts](../../../components/text-input/src/TextInput.types.ts).
-   События типизируй для фактического элемента: например, `ChangeEventHandler<HTMLInputElement>`.
    Для `forwardRef` первым generic передавай тип DOM-элемента, вторым — props.
-   Сохраняй связь generic-параметров между входом и результатом. Callback с произвольным
    набором аргументов описывай через tuple, включая optional и rest-аргументы,
    а не расширяй его до `(...args: unknown[]) => void`.

```ts
export interface IDelayedCallback<TArgs extends Array<unknown>> {
    (...args: TArgs): void;
    cancel: () => void;
}
```

-   Для tuple-результата хука сохраняй тип и порядок каждого элемента; полезны именованные
    элементы tuple. Для вариантов поведения используй union, если он точнее независимых флагов.
-   Экспортируй контракт из `src/index.ts`, обычно через `export type`.
    Не удаляй существующие типовые, именованные и default-экспорты при реорганизации файлов.

## Проверка контракта

-   При изменении generic, props, ref или экспортов добавляй содержательные `*.tests-d.ts`
    с `expectTypeOf` из Vitest. Импортируй API через `./index`, чтобы проверять контракт пакета.
-   Проверяй вывод типов, допустимые аргументы, возвращаемое значение и значимые ограничения.
    Отрицательный пример оформляй с `@ts-expect-error` и объяснением ожидаемой ошибки,
    а не с `@ts-ignore`.
-   Образцы: [useDebouncedCallback.tests-d.ts](../../../hooks/use-debounced-callback/src/useDebouncedCallback.tests-d.ts)
    и [TextInput.tests-d.ts](../../../components/text-input/src/TextInput.tests-d.ts).
-   Из корня запускай `npm test -- <каталог-пакета>/src`: корневой скрипт включает `--typecheck`.
    Затем собирай изменённый пакет с зависимостями и проверяй декларации в `dist`.
    Runtime-тесты сами по себе не доказывают корректность `.d.ts`.
